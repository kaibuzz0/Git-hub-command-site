# Connected Repository Protocol

A connected repository exports one bounded JSON snapshot. The hub never needs a copy of the repository codebase.

## Fast path

1. Add or adapt `connectors/export_repo_snapshot.py` in the connected repository.
2. Generate a schema-v1 snapshot from canonical repository data.
3. Publish the snapshot through an approved GitHub-hosted HTTPS endpoint:
   - `raw.githubusercontent.com` for a committed snapshot, or
   - public `*.github.io` output generated by that repository's Pages build.
4. Add one hub registry entry to `data/repositories.json`:

```json
{
  "id": "my-repo",
  "snapshot_url": "https://OWNER.github.io/REPO/data/repo-snapshot.json",
  "enabled": true
}
```

5. The hub sync workflow fetches the snapshot, validates `repo.id`, size and structure, combines it with other repositories, and republishes the static site.

A checked-in `data/repos/<id>.json` can serve as a transparent last-known-good fallback. A valid freshly fetched remote snapshot takes precedence for that build.

## Snapshot identity

Required: `schema_version`, `repo.id`, `repo.full_name`, `repo.url`, `repo.default_branch`, `generated_at`, `source_commit`.

Supported bounded collections include: `stats`, `tools`, `toolsets`, `cases`, `opportunities`, `intelligence`, `sources`, `prompts`, `evidence`, `agent_ops`, `activity`, and `links`.

Collections contain metadata and links, never credentials, secrets, private file bodies, or unbounded repository content.

## Recommended connected-repo workflow

```text
canonical repo state
   ↓
repo/site data builders
   ↓
command-site snapshot exporter
   ↓
validate locally/CI
   ↓
publish snapshot
   ↓
hub sync + validation
   ↓
aggregate site data
   ↓
Pages
```

Do not hand-maintain a snapshot if the same facts already exist in canonical registries. Generate it.

## Refresh behavior

The hub rebuilds on its own commits and on a schedule. A connected public repository can therefore update its own snapshot without writing directly into the hub. A future GitHub App or repository-dispatch connector can make refresh effectively immediate without weakening this data contract.

## Failure behavior

- Invalid remote JSON is not promoted.
- A mismatched `repo.id` is rejected.
- Oversized snapshots are rejected.
- Unapproved hosts are rejected.
- A remote failure appears in sync health rather than being silently hidden.
- A valid checked-in fallback may continue to represent the last known good state.

## Security boundary

A snapshot is data, not authorization. Security targets, bounty listings, URLs, or program names do not authorize testing.
