# GitHub Command Site Architecture Blueprint

## Purpose

Build one advanced static web application that can visualize and navigate many GitHub repositories without copying their codebases into the hub and without hand-editing the website for normal repository changes.

The GitHub repository is the engineering/source-of-truth layer. GitHub Pages is the user-facing interface.

## Core model

```text
SOURCE REPOSITORIES
    │
    │ canonical project state
    ▼
BOUNDED REPOSITORY SNAPSHOTS
    │
    │ approved GitHub-hosted HTTPS transport
    ▼
CENTRAL SNAPSHOT REGISTRY
    │
    ▼
SYNC + VALIDATION
    │
    ├─ invalid remote data => surfaced as sync error
    ├─ valid remote data   => current build input
    └─ local snapshot      => optional last-known-good fallback
    │
    ▼
AGGREGATE HUB DATA
    │
    ▼
STATIC VS CODE-STYLE COMMAND UI
```

## Hub responsibilities

`kaibuzz0/Git-hub-command-site` owns:

- the generic UI shell and interaction code;
- snapshot schema and validation rules;
- connected-repository registry;
- remote snapshot synchronization;
- aggregate cross-repository data generation;
- cross-repository search/filter/navigation;
- health and sync reporting;
- PWA/installability support;
- CI diagnostics;
- GitHub Pages deployment;
- hub-specific agent governance and handoffs.

The hub should not become a mirror of every repository file. It consumes bounded project metadata.

## Connected repository responsibilities

A connected repository remains authoritative for its own state. It should export a snapshot from canonical project data rather than maintain a second manual database.

A snapshot may include:

- repository identity and source commit;
- repository health/stats;
- tools;
- toolsets;
- structured cases/projects;
- opportunities;
- intelligence/research records;
- source-health records;
- prompts;
- bounded evidence metadata/hashes;
- Agent Operations state;
- recent activity;
- stable links.

It must not include credentials, secrets, private keys, wallet seeds, private data, unbounded repository file bodies, or uncontrolled scan output.

## Transport modes

Preferred transports are intentionally narrow:

1. `raw.githubusercontent.com` for a committed public snapshot.
2. Public `*.github.io` Pages output generated by the connected repository.
3. Checked-in `data/repos/<repo-id>.json` in the hub as a transparent last-known-good fallback.

Adding broader transport mechanisms should preserve host validation, size limits, provenance, and schema validation.

## Refresh model

The static website does not poll private GitHub APIs from the browser. Instead:

```text
connected repo changes
    ↓
connected repo rebuilds/publishes its snapshot
    ↓
hub scheduled or push-triggered sync fetches snapshots
    ↓
hub validates and aggregates
    ↓
GitHub Pages deploys
    ↓
user refreshes the command site
```

Future repository-dispatch or GitHub App events can make refresh near-immediate without changing the snapshot contract.

## UI principles

The web app should behave like a compact engineering workspace:

- VS Code-inspired dark layout;
- repository filter and global workspace mode;
- dynamic Explorer collections;
- command palette;
- global search;
- repository health and sync state;
- per-repository drill-down;
- collection detail views;
- relationship navigation between case/source/tool/evidence records;
- recent activity and opportunity radar;
- PWA installability;
- no bespoke HTML edit for normal repo/tool/toolset/data additions.

## Scaling principle

Repository #2 and repository #200 should use the same integration contract. Scaling should mostly mean adding a validated registry entry and snapshot, not cloning frontend code or inventing new storage systems.

## Integrity rules

- Current source repository state outranks cached hub state.
- Snapshot provenance must include `generated_at` and `source_commit`.
- Invalid remote snapshots never silently replace known-good data.
- Duplicate repository IDs are rejected.
- Public URLs are data, not security-testing authorization.
- Connected repositories remain isolated; the hub must not grant one repo authority over another.
- New collection types should extend the shared schema/aggregator/renderer deliberately.

## Current proof-of-concept

`kaibuzz0/cipher-solving-suite` is the first production spoke. Its own Pages build generates `data/repo-snapshot.json` from canonical tools, toolsets, cases, opportunities, intelligence, source health, prompts, evidence metadata, Agent Ops, stats, links, and recent commit activity. The hub registry consumes that published snapshot.

This first integration is the reference implementation for future repository connectors.
